## 1. 结论与范围锁定

KirinDesk 继续使用现有 TypeScript、React、NestJS、PostgreSQL 单仓库和已经验证的安全资产，采用“产品主线重做、底层资产选择性复用、数据库优先做兼容性加法”的整改路线。不得把此结论理解为在现有页面上继续堆入口，也不得理解为无迁移计划的全量推倒重写。

负责人已将首个付费场景锁定为完整十二步：客户询盘 -> 供应商报价撮合 -> 业务员选价和毛利预警 -> PI 与客户确认 -> 收款闸门 -> 采购申请与执行 -> 到货/QC -> 发货与签收 -> 财务核对 -> 利润核算 -> 提成候选 -> 提成锁定；样品单专用流程和完整售后流程也纳入首个付费版本。该范围显著大于原建议的“询盘到采购闸门”纵向切片，阶段 2 可以分段交付证据，但只有全范围通过门禁才算首个付费场景完成。

DeepSeek 被确认成真实增强项：阶段 2A 必须接入真实 provider，并在超时、限流、解析失败时保留明确失败状态和人工校正路径；mock 不计完成。订单采用“聚合状态 + 子资源独立状态”，样品单和售后以独立资源建模。供应商多轮还价仅保留当前有效报价，不向业务用户提供不可变报价版本；已被选中的报价仍必须通过选价快照冻结，报价覆盖必须进入防篡改审计。

阶段 0 只交付规格、取舍和验收基线。Kai 独立审核通过前，不开始业务实现，不推送分支，不创建合并请求，不触碰生产凭据或客户数据。

## 2. 目标客户、角色与数据边界

### 2.1 已确认的目标客户

首发目标客户是中型多部门外贸公司，强调部门分工、多级审批和更复杂的权限边界。默认模型必须支持业务、采购、财务和管理职责分离，以及可配置的多级采购/售后审批；微型团队的角色兼任和流程简化不是首发验收基线，后续只能通过明确配置支持，不能弱化服务端权限。

### 2.2 角色

| 角色 | 主要任务 | 必须可见 | 服务端禁止返回 |
| --- | --- | --- | --- |
| 业务员 | 询盘、选价、PI、订单、收款、发货和收货 | 客户资料、采购价、毛利、自己负责的订单 | 供应商名称、联系人、联系方式及可反推出供应商身份的字段 |
| 采购员 | 供应商报价、采购执行、到货和 QC | 供应商资料、产品需求、客户国家、采购单和采购异常 | 客户名称、联系人、联系方式及客户原文中的可识别信息 |
| 部门审批人 | 按冻结的审批步骤处理采购和售后决定 | 当前审批所需的最小业务摘要、金额、异常和历史决定 | 未进入本人步骤的详情、其他部门非必要数据、其他租户数据 |
| 管理员/老板 | 审批、配置、异常和经营视图 | 租户内获授权的完整业务数据 | 其他租户数据 |
| 财务 | 收付款核对、成本、利润和提成核对 | 租户内财务数据及必要业务凭证 | 未授权平台数据；默认不直接修改业务原始记录 |
| 平台超管 | 租户治理与经授权的支持访问 | 平台数据、授权范围内的支持数据 | 未获客户授权的租户业务数据 |

字段隔离必须由 API 查询投影、DTO 序列化和权限测试共同保证，不能只靠前端隐藏。所有新增租户业务表必须带 `tenant_id`，启用并强制 RLS，同时在应用事务中设置 tenant context。

## 3. 端到端业务流程

| 步骤 | 角色与入口 | 输入 | 状态变化 | 持久化输出 | 异常与审计 |
| --- | --- | --- | --- | --- | --- |
| 1. 询盘 | 业务员新建询盘 | 客户代号、国家、客户原文、多产品行、目标价 USD | `draft -> submitted` | 询盘头、产品行、原文/解析版本、负责人 | 重复客户提醒；记录创建、解析、提交和改派 |
| 2. 报价撮合 | 采购员处理待报价任务 | 脱敏需求、供应商、报价原文、原子报价行、有效期 | 询盘 `submitted -> quoting -> quoted` | 当前有效供应商报价、每个产品行的多个报价选项、覆盖审计 | 解析失败可重试/人工校正；采购员响应中不含客户身份 |
| 3. 选价与 PI | 业务员选择报价并录销售价 | 中标报价、销售单价、PI 产品子集、付款条件 | 询盘 `quoted -> selected`；PI `draft -> issued -> customer_confirmed` | 选价快照、毛利率、PI 版本与文件、正式客户和销售订单草稿 | 低于阈值告警；失效报价阻断；记录选价和客户升级 |
| 3.5 收款闸门 | 业务员记录到款 | 金额、币种、日期、方式、凭证、关联 PI/订单 | 收款 `recorded -> confirmed/rejected`；订单采购闸门开/关 | 可追溯收款流水，不代表第三方支付成功 | 重复流水、金额不足、凭证缺失；配置关闭时记录绕过原因 |
| 4. 采购申请 | 业务员发起，部门审批人按冻结步骤审批 | 已确认订单行、选中报价、所需数量 | `draft -> pending_approval -> approved/rejected/withdrawn` | 采购申请及行、多级不可变决定；批准后按供应商生成多张采购单 | 未满足收款闸门或未完成全部步骤时阻断；审批决定追加写审计账本 |
| 5. 采购执行 | 采购员下单 | 预计价、最终采购价、采购付款可选记录 | 采购单 `approved -> placed -> received/closed` | 最终价格快照、采购付款、差异异常 | 最终价偏差触发异常；修改必须保留前值和操作人 |
| 6. 到货验货 | 采购员，按配置增加业务员确认 | 到货数量、质量结果、照片、备注 | 收货单 `pending -> inspected -> accepted/rejected` | 分批到货、QC 结果、附件、确认记录 | 数量/质量差异异常；双确认配置必须服务端执行 |
| 7. 发货 | 业务员 | 发货批次、物流单号、承运方、数量、费用和折 RMB 汇率 | 发货 `draft -> dispatched` | 发货批次、行、物流事件、多币种费用快照 | 超可发数量阻断；费用或汇率缺失进入财务异常 |
| 8. 收货与尾款 | 业务员 | 签收日期、凭证、每笔到款 | 发货 `dispatched -> delivered`；收款独立推进 | 签收凭证和追加式收款流水 | 收货与收款不得耦合；分批发货可关联分批收款 |
| 9. 财务核对 | 财务 | 费用、采购成本、运费和收款凭证 | 核对 `pending -> verified/returned` | 每项核对结果、打回原因、核对人和时间 | 缺成本/运费/收款报警；财务只核对或打回，不改原始记录 |
| 10. 利润核算 | 系统 | 销售收入、采购成本、物流费用、其他费用、退款赔偿、汇率快照 | 利润快照 `provisional -> final` | 毛利、净利、公式版本、输入快照 | 缺失项不产出“最终利润”；固定成本不摊入单订单 |
| 11. 提成候选 | 系统 | 可选基数、人员比例、提成表版本、最终利润数据 | `draft -> calculated` | 销售/采购提成候选与计算快照 | 无有效规则或利润未最终核对时阻断 |
| 12. 提成锁定 | 管理员 | 候选提成及确认意见 | `calculated -> locked`；修订生成新版本 | 不可变结算版本和后续发放记录 | 已锁定版本不可原地修改；所有修订追加版本 |

### 3.1 首发范围内的业务分支

| 分支 | 角色与入口 | 输入 | 状态变化 | 持久化输出 | 异常与审计 |
| --- | --- | --- | --- | --- | --- |
| 样品单 | 业务员从询盘/选价发起，采购员履约，管理员按规则审批 | 样品行、数量、收件信息、费用、承运信息、客户反馈 | `draft -> pending_approval -> approved -> dispatched -> delivered -> confirmed -> converted/closed` | 样品单、样品行、发货/签收、反馈及转正式订单关系 | 跨角色字段脱敏；超量/重复转单阻断；状态、费用和转单快照审计 |
| 售后 | 业务员发起，管理员多级审批，财务执行/核对 | 类型、原因、责任、金额、币种、凭证、关联订单/发货 | `draft -> pending_approval -> approved/rejected -> executing -> completed -> closed` | 售后工单、审批决定、退款/赔偿调整流水、新利润与提成修订版本 | 重复退款、越权审批、金额超限阻断；不得覆盖原收款、利润或已锁定提成 |

样品转正式订单不得复用可变报价或推断历史价格，必须生成新的选价/PI 快照。售后退款和赔偿通过追加调整流水影响新利润版本；已完成的收款、核对和提成版本保持不可变。

### 3.2 已确认的订单聚合状态机

外部可见的销售订单聚合状态使用：

`draft -> customer_confirmed -> payment_gate_open -> procurement -> fulfillment -> delivered -> finance_review -> settled`

旁路状态为 `cancelled` 和 `on_hold`。采购申请、采购单、收货、发货、收款和财务核对各自维护细分状态，销售订单聚合状态由服务端根据子资源计算，不用一个字段表达所有并行事件。

负责人已确认采用该状态模型。退款、售后、重开核算不通过把订单简单倒退到旧状态实现，而是追加调整记录并生成新利润和提成版本。

## 5. MVP 边界

### 5.1 已确认纳入首个付费场景

- 完成第 3 节定义的十二步主流程，并覆盖每一步的角色、状态、输入、输出、异常和审计。
- 业务员创建多产品询盘，采购员只能看到脱敏需求。
- 一个询盘产品行可接收多个供应商报价；报价包含有效期，只保留当前有效结果，覆盖操作进入审计。
- 业务员可见采购价但不可见供应商身份，选择报价后录入销售价并获得精确毛利率和阈值告警。
- 从选定产品生成一份 PI；客户确认后建立一份销售订单。
- 记录真实发生的定金/全款及凭证；满足租户配置后解锁采购申请。
- 支持多级采购/售后审批、采购拆单、到货/QC、分批发货、签收、财务核对、利润和提成锁定。
- 支持样品寄送、客户确认、关闭和转正式订单的专用流程。
- 支持完整售后申请、审批、执行、退款/赔偿调整和关闭流程。
- 所有记录真实持久化、强制 tenant scope/RLS、权限投影和审计。
- DeepSeek 必须使用真实测试 provider、结构化输出校验、超时/限流/失败重试和人工校正，不把 provider mock 当成功路径。

### 5.2 首个付费场景明确不包含

- 第三方在线支付、退款回调和自动对账；MVP 只记录线下/外部渠道已经发生的收款事实。
- OCR、自动报关、支付、市场实时汇率、计费套餐和平台治理扩张。
- 固定成本分摊、复杂会计总账和自动税务处理。
- 对旧前端进行视觉换皮或继续增加全量顶栏入口。

### 5.3 完成定义

十二步主流程、样品单和售后流程必须有真实数据库持久化和自动化端到端测试，角色字段隔离、跨租户、权限越界、多级审批、金额精度、版本修订和审计断言必须通过。DeepSeek 需有真实 provider 成功证据；provider 不可用时必须明确显示失败状态并允许人工校正继续业务。缺失真实集成不能标记 AI 完成，临时 provider 故障也不能破坏人工主流程。任何 mock、占位页、手工 SQL 或只靠人工验证的路径均不计完成。

## 6. 最小数据模型

以下为概念模型，字段名会在对应阶段的迁移设计中冻结。所有租户业务实体默认含 `id`、`tenant_id`、审计时间和必要的软删除字段。

| 实体 | 关键字段/关系 | 约束与说明 |
| --- | --- | --- |
| `inquiries` | owner、lead code、country、raw text、status | 提交后原文修改需形成版本；客户身份字段不得暴露给采购员 |
| `inquiry_items` | inquiry、line no、description/spec、quantity、unit、target price USD | 一询盘多行；金额和数量使用 numeric/decimal |
| `supplier_quotes` | supplier、inquiry、lock version、raw text、currency、valid until、status | 每个供应商/询盘保留当前有效报价；覆盖前后值写入 hash 链审计，已选报价由选价快照保留 |
| `supplier_quote_lines` | quote、inquiry item、variant key/value、quantity、unit price、terms | “一变量一行”；必须指向同租户询盘和报价 |
| `quote_selections` | inquiry item、quote line、purchase snapshot、sales price、margin snapshot | 选择时冻结价格、币种、汇率、公式版本；API 对业务员隐藏供应商外键投影 |
| `proforma_invoices` | inquiry、customer、sales order、PI no、version、currency、payment terms、status、file | 1 PI 对应 1 销售订单；一个询盘可对部分产品生成多份 PI |

| 改造 `purchase_order_items` | request item、expected price、final price、variance | 最终价修改需版本/审计；差异规则可配置 |
| `goods_receipts` / `goods_receipt_items` | purchase order、batch、received quantity、QC status、photos、confirmations | 支持分批到货与可配置双确认 |
| `shipments` / `shipment_items` | sales order、batch、tracking、carrier、status、quantity | 多批发货，不能超过可发数量 |
| `sample_orders` / `sample_order_items` | inquiry/selection、recipient、items、status、shipment、converted order | 样品流程独立；转单冻结来源并以唯一约束防止重复转换 |
| `order_expenses` | order/shipment、type、amount、currency、fx snapshot、amount RMB | 每笔费用独立币种和汇率快照 |
| `finance_reviews` / `finance_review_items` | order、subject type/id、decision、reason、reviewer | 财务只追加核对/打回结果，不更新原始记录 |
| `profit_snapshots` | order、revenue/cost/expense/refund inputs、gross/net profit、formula version、status | 输入完整才可 final；修订生成新版本 |
| 改造 commission | basis type、role type、user rate、profit snapshot、locked version | 基数支持销售额/毛利/净利，销售与采购规则分开 |
| `after_sales_cases` / `after_sales_adjustments` | order/shipment、type、reason、amount、currency、workflow、status | 完整售后流程；退款/赔偿只追加，关联新利润和提成修订版本 |
| `business_exceptions` | order/context、type、severity、status、assignee、resolution | 最少覆盖价差、数量差、费用缺失、重复客户 |
| `business_events` | aggregate type/id、event type、actor、occurred at、payload ref | 用于时间线投影；敏感字段不复制进通用 payload |

### 6.1 一致性规则

- 外键关联同时校验 `tenant_id`；仅靠 UUID 外键不足以证明同租户。
- 金额使用 `numeric`，应用层使用现有 BigInt/decimal 工具；每次换汇保存原币金额、币种、汇率、来源、时间和折算结果。
- 报价只保留当前业务记录，其每次覆盖必须进入 hash 链审计；选价、PI、最终采购价、利润和提成以不可变版本或快照保证历史可追溯。
- 所有附件通过文件资源关联；业务 DTO 不返回存储 object key。
- 角色字段隔离在查询/序列化层显式 allowlist，并配反向断言测试。

## 8. 数据迁移和回滚原则

### 8.1 迁移

1. 新业务表和可空关联先以向后兼容方式添加，不删除 v1 表或字段。
2. 旧客户、供应商和订单继续可读；新流程使用显式来源/版本字段，避免把历史记录伪装成已走完整新流程。
3. 需要回填时先生成只读盘点和对账结果，再分批迁移；跨币种历史订单不得臆造汇率。
4. 每次迁移包含向下脚本或明确的前滚恢复方案；不可逆数据变换必须单独升级审批。
5. 先在隔离数据副本演练，验证数量、金额、租户归属、孤儿记录和 hash 链，再允许进入发布候选。

### 8.2 回滚

- 阶段 0 文档回滚：删除本文件或回退文档提交，不影响运行时和数据。
- 阶段 1 工程改造：保留原启动路径，按提交回退；会话模型切换需支持旧令牌的明确失效策略。
- 阶段 2 新流程：按 2A-2G 使用独立租户级 feature flag 隐藏未通过的入口；回滚应用时保留已写入的新表数据，禁止以删表作为常规回滚。样品和售后数据回滚后保持只读可追溯，不得删除调整流水。
- 迁移失败：停止写入、恢复应用旧版本、保留迁移日志并从已验证备份恢复；未完成对账不得继续发布。
