# 阶段 2C：采购申请、审批与拆单交付说明

- 状态：待 Kai 独立评审
- 分支：`feat/kir-8-stage-2c`
- 前置：阶段 2B 的冻结选价、PI 来源销售订单、追加式收款和采购闸门

## 结论

采购申请、冻结多级审批、追加式决定、按供应商拆单、销售订单与采购单显式关联、下单前闸门复核、最终采购价和价差异常已经使用真实 PostgreSQL 持久化实现。申请创建和采购单下单都由服务端读取最新闸门评估；下单事务与闸门评估事务使用同一销售订单行锁串行化，并在取得锁后重读最新闸门。任何审批步骤未完成时不会生成采购单。业务员的申请和自动采购单响应使用服务端字段投影隐藏供应商身份，不能通过 v1 通用采购单更新、删除或旧单级审批接口绕过新流程。

本阶段不宣称已实现采购前端页面、供应商电子下单、采购付款、到货/QC 或外部汇率服务。`placed` 只代表租户内部已确认向供应商下单，未向供应商系统发送或验证电子订单。

## 范围与验收

| 验收项 | 实现与证据 |
| --- | --- |
| 收款闸门阻断 | 创建采购申请和 `approved -> placed` 都读取该销售订单最新的 `procurement_gate_evaluations`；只有 `open` 或带审计原因的 `bypassed` 可继续。下单与闸门评估先竞争同一销售订单行锁，锁后重读闸门；确定性并发测试通过 PostgreSQL 阻塞关系证明下单等待未提交的关闭评估，并在其提交后 fail-closed。 |
| 冻结多级审批 | 租户管理员每次配置生成新版本；申请复制配置步骤、版本和价差阈值。配置 v2 激活后，既有 v1 申请仍按两步顺序审批。 |
| 决定不可覆盖与职责分离 | 决定表只授予应用角色 `SELECT/INSERT`，数据库触发器禁止更新/删除；申请人不能出现在本申请冻结审批流中，决定必须由当前步骤指定且具备全域审批权限的用户追加。 |
| 按供应商拆单与显式关联 | 最终批准事务按供应商和采购币种分组生成采购单；`sales_order_purchase_orders` 追加写入销售订单、采购申请和采购单三方关系。一个供应商存在多币种时，为保持采购单头单币种约束，会生成多张采购单。 |
| 供应商身份投影 | `own` / `assigned` 范围的申请人响应不返回申请行或采购单的 `supplier_id`；即使从旧 `/api/purchase-orders/:id` 读取自动采购单也不返回。供应商过滤不作用于受限用户的自动采购单，避免查询侧信道。 |
| 精确最终价与差异异常 | 预计单价来自不可变选价 JSON 快照；预计行金额、最终行金额、价差金额和价差基点均由 PostgreSQL `numeric` 计算。超过冻结阈值时追加 `purchase_price_snapshots`、打开 `business_exceptions.price_variance` 并写入 hash-chain 审计。 |

## 业务闭环

1. 全域采购审批管理员提交审批人顺序和价差阈值，服务端追加新的活动配置版本并停用旧版本。
2. 业务员从 PI 来源销售订单选择一个或多个冻结选价并填写所需数量。
3. 服务端锁定销售订单，验证最新收款闸门、活动审批配置、申请人与审批人职责分离、选价归属及累计申请数量不超销售订单数量。
4. 申请以 `pending_approval` 创建，冻结闸门评估、审批配置版本、审批步骤、供应商、采购币种、预计单价、数量和选价 JSON。
5. 当前步骤指定审批人按顺序追加 `approved` 或 `rejected` 决定；拒绝需要原因。申请人可在最终决定前填写原因撤回。
6. 只有全部步骤均批准时，服务端在同一事务内将申请置为 `approved`，按供应商和币种生成状态为 `approved` 的采购单及行，并写显式订单关联。
7. 采购员提交每一采购单行的最终单价。服务端再次校验最新闸门和申请完成状态，计算精确价差、追加价格快照和必要异常，再把采购单置为 `placed`。

## 数据模型与数据库保护

`047_stage_2c_procurement_requests.sql` 是加法迁移，新增：

- `procurement_approval_configs` / `procurement_approval_config_steps`：租户审批配置版本和不可变步骤。
- `procurement_requests` / `procurement_request_items`：销售订单来源、闸门快照、配置版本、申请行和预计采购价。
- `procurement_request_approval_steps`：创建申请时复制的冻结审批实例。
- `procurement_request_decisions`：按步骤唯一的追加式批准或拒绝决定。
- `sales_order_purchase_orders`：销售订单、采购申请和自动采购单的不可变显式关联。
- `purchase_price_snapshots`：预计价、最终价、数量、行金额、价差、阈值、公式和操作人的不可变快照。

迁移改造 `purchase_orders` 和 `purchase_order_items`，加入采购申请来源、预计/最终总额、下单事实、申请行来源、选价来源、最终价和差异字段。自动采购单的冻结内容由数据库触发器保护；v1 通用服务也显式拒绝修改、删除或旧审批自动采购单。

所有新增业务表都包含 `tenant_id`、复合租户外键、`ENABLE/FORCE RLS` 和最小应用角色授权。配置步骤、申请行、冻结步骤、决定、订单关联和价格快照均禁止应用角色更新或删除，并由数据库触发器防止高权限误改。

## API

审批配置：

- `GET /api/procurement/approval-config`
- `PUT /api/procurement/approval-config`

采购申请：

- `POST /api/sales-orders/:id/procurement-requests`
- `GET /api/sales-orders/:id/procurement-requests`
- `GET /api/procurement-requests/:id`
- `POST /api/procurement-requests/:id/decisions`
- `POST /api/procurement-requests/:id/withdraw`

采购下单：

- `POST /api/purchase-orders/:id/place`

现有 `GET /api/purchase-orders` 和 `GET /api/purchase-orders/:id` 对自动采购单增加服务端供应商字段投影；现有更新、删除和旧审批端点对自动采购单返回 `GENERATED_PURCHASE_ORDER_IMMUTABLE`。

## 迁移与回滚

UP 不删除或改写 v1 采购数据；历史采购单和行的新字段保持 `NULL`，仍由旧接口管理。新采购流程只处理带 `source_procurement_request_id` 的自动采购单。

DOWN 会删除采购申请、冻结审批、决定、显式订单关联、最终价快照及自动采购单的新增来源和价格字段，因此会丢失本阶段全部新增业务事实。若已经生成采购单，执行前必须备份新增表和扩展列。处于 `placed`、`received` 或 `closed` 的采购单会确定性降级为 `completed`，细分状态不可逆。常规应用故障应优先前滚修复或只回滚应用入口，不应执行迁移 DOWN。

代码回滚必须同步移除 `ProcurementModule`，并恢复 v1 采购单响应和更新路径。只回滚前端无数据影响；本阶段尚未交付采购前端。只回滚迁移而保留 API 会导致请求失败，不是支持的拆分状态。

## 风险与未完成项

- 本阶段只交付可测试 API 纵向闭环，没有采购前端页面；不能把 API 完成描述成可视化采购工作台完成。
- 审批步骤当前冻结具体用户，不支持按岗位动态解析或临时代理；人员变更通过创建新配置版本处理，不修改既有申请。
- 自动采购单按供应商和币种分组；同一供应商对同一销售订单存在多个采购币种时会拆为多张采购单。
- 最终采购价保留原采购币种精确快照；未接入外部汇率或折算为租户基准币种，不能据此宣称采购成本 RMB 已最终核对。
- `placed` 是内部事实，不代表供应商系统已接收；供应商电子下单、回执、采购付款和对账需后续单独立项。
- 迁移 DOWN 具有业务数据破坏性，只允许在隔离测试库演练；生产发布失败优先应用回滚或前滚修复。
- 当前工作树继承阶段 2A、2B 和 2G 的未提交前置改动；本说明只陈述 2C 增量及组合工作树验证结果，不得把前置内容混称为本阶段独立提交。

除上述明确边界外，本阶段验收范围内没有已知未完成项。
