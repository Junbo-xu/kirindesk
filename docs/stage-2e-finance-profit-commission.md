# 阶段 2E：财务核对、利润与提成

## 1. 交付范围与验收

本阶段建立在阶段 2B 的 PI/收款、阶段 2C 的最终采购价和阶段 2D 的费用/签收事实之上，交付以下真实持久化能力：

- 财务对已签收订单追加记录核对通过或打回决定；打回原因、缺失项、逐项金额和换汇证据随版本保存。
- 收款、采购成本和订单费用只作为只读来源。财务核对不会更新或覆盖这些业务原始记录。
- 暂算和最终利润均为不可变快照，冻结公式版本、来源指纹、完整输入、核对版本和人民币结果。
- 缺收款、最终采购价、运费、费用汇率或当前有效核对时，只允许暂算；最终利润 fail-closed。
- 提成候选只连接当前最终利润，支持销售额、毛利或净利三种基数，分别保存销售和采购两套规则。
- 每套提成按人员基点分配，人员不重复且每个角色合计必须为 10,000 基点；金额按整数分逐人半入计算。
- 候选锁定是独立追加事实。锁定后不得修改旧候选，只能填写修订原因并创建连接旧版本的新候选。
- 财务工作台覆盖订单、来源、缺失项、汇率、核对历史、利润、规则、人员分配、锁定和修订；无权限角色不显示入口且直达返回禁止页。

本阶段不包含银行/支付渠道自动对账、外部汇率供应商、退款/售后事实录入、提成发放、会计凭证或税务处理。`refund_rmb` 在当前公式中冻结为 `0.00`；出现真实售后退款需求时必须先新增不可变退款来源，再发布新公式版本，不能修改历史快照。

## 2. 服务端契约

### 2.1 财务核对

- `GET /api/finance/orders`
- `GET /api/finance/orders/:id`
- `POST /api/finance/orders/:id/reviews`

只有来源于 PI 且状态为 `delivered`、`finance_review` 或 `settled` 的订单进入财务列表。写操作要求 `all` 数据范围，避免以本人范围完成自核对。核对服务在同一租户事务内重新读取已确认收款、采购最终价和冻结费用并生成 SHA-256 来源指纹。

外币收款和采购成本必须同时提供汇率、来源和采集时间；RMB 来源固定使用 `currency_identity`。`verified` 要求缺失项为空，`returned` 要求非空原因。每次决定都会新增 `finance_reviews` 和逐项 `finance_review_items`，并写入审计链；业务来源表不参与更新。

### 2.2 利润快照

- `POST /api/finance/orders/:id/profit-snapshots`

公式 `order_profit_rmb_v1`：

`毛利 = 销售收入 - 采购成本`

`净利 = 毛利 - 运费 - 其他费用 - 退款`

金额先在 PostgreSQL `numeric` 中换算为人民币两位小数，再以字符串进入整数分运算，避免 JavaScript 浮点参与持久化计算。最终快照必须连接输入指纹仍与当前来源一致的最新 `verified` 核对；来源变化会使旧核对和旧最终利润失效，但不会改写它们。暂算保留缺失项并明确标记 `provisional`。

### 2.3 提成规则、候选与锁定

- `GET /api/finance/commission-rules`
- `PUT /api/finance/commission-rules`
- `POST /api/finance/orders/:id/commission-candidates`
- `POST /api/finance/commission-candidates/:id/lock`

规则按 `sales`、`procurement` 分别追加版本，基数为 `sales_revenue`、`gross_profit` 或 `net_profit`，比例使用整数基点。候选计算再次校验最新利润为 `final`、来源指纹未变，且连接当前最新的 `verified` 核对，然后使用两套当前规则；负利润基数按零计提。候选冻结规则版本、利润版本、人员比例、舍入策略和全部结果。

锁定事务先锁销售订单以串行化候选状态，然后重新校验当前最终利润与最新 `verified` 核对，并确认候选仍连接该利润版本，再新增 `commission_candidate_locks_v2`；不会更新候选行。因此候选计算后若来源变化、利润被新版本取代或财务追加打回，旧候选会 fail-closed，不得锁定。锁定后的下一次计算必须带修订原因并通过 `supersedes_id` 连接旧候选；若未锁候选已因新的最终利润失效，也允许带修订原因追加替代版本，避免旧候选既不能锁定又不能替换。对连接同一当前利润的未锁候选，仍严格要求先锁定再修订。锁定成功后订单可由 `finance_review` 推进到 `settled`，但历史财务和提成事实保持不变。

## 3. 数据、权限与隔离

迁移 `049_stage_2e_finance_profit_commission.sql` 新增：

- `finance_reviews`、`finance_review_items`
- `profit_snapshots`
- `commission_rule_versions_v2`
- `commission_candidates_v2`、`commission_candidate_lines_v2`
- `commission_candidate_locks_v2`

所有表都有 `tenant_id`、租户复合外键、`ENABLE/FORCE ROW LEVEL SECURITY` 和同一租户读写策略。应用角色只拥有 `SELECT, INSERT`；数据库触发器与显式撤销共同拒绝 `UPDATE, DELETE`。跨版本外键均为 `ON DELETE RESTRICT`。

产品权限 seed 新增：

- `finance_reviews:view`、`finance_reviews:review`
- `profit_snapshots:create`
- `commission_rules:manage`
- `commission_candidates:calculate`、`commission_candidates:lock`

这些权限不授予默认销售角色。审计投影把新版核对、利润和提成资源统一映射到 `finance_reviews:view`，避免沿用旧提成查看权限造成字段泄漏。部署既有环境时必须先执行迁移，再运行幂等权限 seed，最后发布 API/Web；缺少权限 seed 时新版操作应保持不可用。

## 5. 迁移、风险与回滚

迁移为纯增量建表，不回填旧订单，也不会把既有订单伪装成已完成财务核对。满足上游来源与状态条件的历史订单会出现在待核对列表，但必须由财务显式追加决定后才能生成最终利润。

`049` DOWN 会按依赖顺序删除全部阶段 2E 核对、利润、规则、候选、人员行和锁定事实，属于有数据损失的回滚。生产候选一旦存在阶段 2E 数据，禁止直接执行 DOWN；必须先停止相关写入、备份数据库、导出逐订单版本链和审计校验结果，并由负责人单独批准。应用回滚应先回退 Web/API，再决定是否保留只读新表；权限 seed 产生的全局权限行可暂时保留，不应为了回滚而破坏既有角色审计关系。

已知风险与后续边界：

- 手工汇率来源仍依赖操作人员提供真实凭证；外部供应商接入需另立项处理成本、幂等、失败和对账。
- 当前候选是应计结果，不是已发放工资；发放、撤销和会计期间仍沿用独立提成发放域，不由阶段 2E 锁定替代。
- 来源指纹可使旧结果失效，但不会自动生成修订；新增售后或费用事实后必须由财务显式复核并追加版本。
- 新表无历史回填；迁移前后的经营汇总不得混用为同一口径，报表接入需要明确公式版本筛选。
